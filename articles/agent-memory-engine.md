## Who and what

This is a local memory and project-knowledge runtime for coding agents. Its MCP server accepts task context, retrieves a combined context pack, and accepts a post-task reflection. Agent-facing tools are wrappers around service and retrieval layers; this review makes no claim about production deployment, user adoption, or benchmark performance.[[README.md — project description and MCP tools](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/README.md)] [[memory_engine/mcp/tools.py — tool handlers](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/mcp/tools.py)]

## Architecture and data model

**Code observation.** The repository separates compressed engineering memory from source-grounded knowledge. A `MemoryNode` is a project-owned tree record with title, summary, kind, tags, status, confidence, importance, parent/depth, optional module and source references, branch metadata, trust and verification fields, and attached evidence. A `MemoryCandidate` is the staging record used before promotion. Evidence records retain content, an optional source, and a creation time. SQLAlchemy maps these records to SQLite tables.[[memory_engine/models/domain.py — MemoryNode, MemoryCandidate, Evidence](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/domain.py)] [[memory_engine/models/orm.py — MemoryNodeORM, EvidenceORM, MemoryCandidateORM](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/orm.py)]

The project-local MCP runtime stores its SQLite database at `.memory-engine/memory.db`; the optional persistent vector database is `.memory-engine/vector.db`. Project state and an incremental-index manifest live alongside them. These paths are implementation configuration; they do not imply that every interface uses the same database location.[[memory_engine/bootstrap/local_storage.py — ProjectLocalStorage.db_path and vector_db_path](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/bootstrap/local_storage.py)]

Knowledge ingestion stores redacted source documents and chunks separately from memory nodes, with source paths, content hashes, heading paths, line ranges, symbols, and index status. FTS5 is the lexical index. Optional semantic embedding is a separate retrieval arm; the README documents it as opt-in. The two domains are combined for retrieval but are not the same record type or lifecycle.[[memory_engine/knowledge/ingestion.py — KnowledgeIngestionService.ingest](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/ingestion.py)] [[memory_engine/knowledge/fts_index.py — FTS5 tables and insert/delete functions](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/fts_index.py)] [[README.md — optional semantic retrieval](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/README.md)]

## Write, update, delete, and retrieval

**Writes and updates — code observation.** `PostTaskService.reflect_and_write` runs a local reflection analysis, skips work when the retention gates fail, stages suggested candidates, and sends each candidate through `PromotionService`. Promotion can create, update, merge, supersede, discard, or set `needs_review`, depending on duplicate similarity, contradiction checks, and confidence. An update replaces a node summary and merges tags; a merge appends a candidate summary; superseding creates a replacement node, marks the old node superseded, and links the two. This is a candidate-based post-task path, not evidence that arbitrary user corrections are recognized correctly. In the inspected update/merge path I did not find a general before/after mutation-history log for the old summary.[[memory_engine/services/post_task.py — reflect_and_write](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/post_task.py)] [[memory_engine/services/promotion.py — _branch, _action_update, _action_merge, _action_supersede](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/promotion.py)]

**Retrieval — code observation.** `RecallService.recall` analyzes task text and file/symbol hints, loads project nodes, scores candidates, applies relevance and constraint-scope gates, then asks `ContextComposer` to fill typed buckets under a token budget. The composer records selected and excluded candidates in a per-signal trace. `KnowledgeSearchService.search` combines FTS5 with a vector-search arm and reranks and trims the results; the vector arm uses an optional persistent semantic index when configured, otherwise the in-process vector index. `UnifiedContextRetrievalService.retrieve` combines memory and knowledge into one context pack. The README and retrieval pipeline document lexical fallback as the default local mode and semantic retrieval as optional. These source paths establish mechanisms, not answer quality or recall accuracy.[[memory_engine/skills/recall.py — RecallService.recall and relevance gates](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/skills/recall.py)] [[memory_engine/skills/composer.py — ContextComposer._fill_bucket and build_provenance](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/skills/composer.py)] [[memory_engine/knowledge/search.py — KnowledgeSearchService.search](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/search.py)] [[memory_engine/knowledge/fusion.py — UnifiedContextRetrievalService.retrieve](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/fusion.py)] [[docs/architecture/retrieval-pipeline.md — documented ranking and budgets](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/docs/architecture/retrieval-pipeline.md)]

The code includes a `needs_review` promotion outcome and the composer emits compact provenance labels for that status. In the inspected `ContextComposer._fill_bucket` exclusion list, stale, superseded, archived, needs-revalidation, and invalidated nodes are excluded, but `needs_review` is not in that list. Thus the review status alone does not prevent this composer path from selecting the node; the project should not be described as automatically withholding all review-flagged memories.[[memory_engine/services/promotion.py — _action_needs_review](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/promotion.py)] [[memory_engine/skills/composer.py — _fill_bucket status filtering](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/skills/composer.py)]

**Deletion.** There are two distinct behaviors. `MemoryService.delete_node` calls the repository's physical delete; attached evidence and relation rows have database cascade relationships. Separately, the retention service archives/compacts lifecycle records, and source validity marks a memory invalidated or needing revalidation without deleting it. Knowledge re-indexing marks replaced chunks and derived records stale. I did not find a single end-to-end deletion operation that coordinates memory nodes, indexed documents, vector records, filesystem manifests, backups, and external copies; erasure completeness is unknown.[[memory_engine/services/memory_service.py — delete_node](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/memory_service.py)] [[memory_engine/repositories/memory_node.py — delete](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/repositories/memory_node.py)] [[memory_engine/models/orm.py — evidence and relation cascades](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/orm.py)] [[memory_engine/services/retention.py — archive, restore, and compaction lifecycle](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/retention.py)] [[memory_engine/services/source_validity.py — source drift transitions](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/source_validity.py)] [[memory_engine/knowledge/ingestion.py — stale prior indexes on update](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/ingestion.py)]

**Scope isolation.** Memory and knowledge rows carry `project_id`, and the retrieval and search paths use project-scoped queries. The MCP tools also validate a supplied workspace root or repository fingerprint against the server project. In compatibility mode, missing workspace context logs a warning and allows the request; strict mode can require it. Constraint scope is separately checked against global, repository, branch, module, path, symbol, or task-intent context. These are source-level isolation and filtering mechanisms; they do not establish a user/team authorization boundary or runtime resistance to cross-project leakage.[[memory_engine/models/orm.py — project_id fields](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/orm.py)] [[memory_engine/mcp/tools.py — _validate_workspace and retrieval context](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/mcp/tools.py)] [[memory_engine/services/constraint_scope.py — constraint_is_eligible](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/constraint_scope.py)]

**Provenance and evidence.** Memory nodes can carry source path/hash/symbol, branch and commit context, trust level, verification-evidence level, and explicit evidence entries. Source validity checks can mark source-backed nodes invalidated when a file disappears or needing revalidation when its evidence drifts; those transitions retain prior status and a reason. Retrieval traces expose score signals and compact provenance. Knowledge chunks include source paths and line ranges. This provides trace and source metadata, not proof that every generated claim is supported by a cited passage. The inspected sources also show that trust and verification are separate metadata, not adjudicated benchmark results.[[memory_engine/models/orm.py — source, trust, verification, and evidence fields](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/orm.py)] [[memory_engine/services/source_validity.py — check and revalidate](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/services/source_validity.py)] [[memory_engine/skills/composer.py — build_provenance](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/skills/composer.py)] [[memory_engine/models/knowledge_domain.py — KnowledgeChunk source fields](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/knowledge_domain.py)]

## Efficiency and latency observability

The retrieval pipeline has a project-scoped in-process TTL cache (five-minute default) whose key includes query, project, file/symbol hints, token budget, and Git context. Cache invalidation is called after ingestion and memory writes. Source-validity work is bounded to at most 50 checks per recall; index refresh tracks file changes through a manifest. These are implementation choices, not measured latency results.[[memory_engine/knowledge/cache.py — SimpleCache and make_key](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/cache.py)] [[memory_engine/skills/recall.py — _MAX_VALIDITY_CHECKS_PER_RECALL](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/skills/recall.py)] [[memory_engine/bootstrap/incremental_index.py — IncrementalIndexCoordinator](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/bootstrap/incremental_index.py)]

The output includes cache-hit state, result counts, and token estimates. I found no latency histogram or exported latency metric in the reviewed runtime; `memory_engine/runtime/observability` is reserved for future logging, metrics, and diagnostics. The unified retrieval source captures a monotonic start time but does not return an elapsed-duration field in the result model. Therefore latency observability is not established by the inspected code. The token count is a deterministic character-based estimate, not a tokenizer measurement.[[memory_engine/knowledge/fusion.py — result fields and retrieval timing](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/knowledge/fusion.py)] [[memory_engine/models/knowledge_domain.py — UnifiedContextPack](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/models/knowledge_domain.py)] [[memory_engine/runtime/observability/__init__.py — reserved module](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/runtime/observability/__init__.py)] [[memory_engine/skills/composer.py — deterministic token estimate](https://github.com/uudam42/agent-memory-engine/blob/6e345342051dea267e465fc24e3e88e326d9ac51/memory_engine/skills/composer.py)]
