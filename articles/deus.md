## Summary and architecture

Deus is a self-hosted personal AI assistant that combines conversational memory, a persistent vault, semantic retrieval, and agent integrations. The README describes capturing conversational facts and recalling them across sessions and channels; its LongMemEval figure is an upstream report, not independently reproduced here.[[README](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/README.md)]

The documented runtime uses one Node.js host process and isolated containers for conversation groups. Channel adapters are MCP child processes; the host routes messages and controls group/container mounts, while a credential proxy injects provider credentials into outbound requests.[[architecture](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/ARCHITECTURE.md)] [[security model](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/SECURITY.md)]

Memory is split across durable Markdown/session files, a SQLite index used by the memory indexer, and a separate SQLite database for the memory tree. The documented tree root, `MEMORY_TREE.md`, is a small human-readable map; the retrieval design explicitly uses flat retrieval over indexed nodes and one-hop `see_also` expansion rather than descending the hierarchy.[[memory indexer](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_indexer.py)] [[memory-tree decision](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/memory-tree.md)] [[memory-tree implementation](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_tree.py)]

The architecture describes extracted atomic facts with confidence, temporal/versioning and domain metadata, alongside entity and relationship extraction. A separate solution-note format stores operational learnings in YAML-frontmatter Markdown files in the vault.[[architecture](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/ARCHITECTURE.md)] [[solution atom schema](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/solution-atom-schema.md)]

## Write, update, delete, and retrieval

**Write and indexing.** Session and vault workflows feed files into the memory system. The memory indexer exposes add, add-directory, extract, query and rebuild paths; it resolves the vault from `DEUS_VAULT_PATH`, then an instance-local `.deus/config.json`, then the global configuration. Solution notes have a UUID, type, title, tags and optional problem/module/severity/update metadata. Their schema describes them as append-only, with list/search/add commands.[[indexer](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_indexer.py)] [[solution atom schema](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/solution-atom-schema.md)]

**Correction and deletion.** The database policy favors marking primary rows inactive with expiry/orphan timestamps, preserving them for audit across reindex and rebuild. Rebuild makes a timestamped database backup first. Fully derived FTS/vector rows can be deleted or rebuilt; vault files follow separate git-versioned lifecycle rules. Because the repository has distinct memory layers and entry types, this policy does not establish one uniform correction or erasure behavior for all of them. Nor does a database soft-delete establish removal from Git history, backups, WAL files or downstream copies.[[database deletion policy](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/no-db-deletion.md)] [[solution atom schema](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/solution-atom-schema.md)]

**Retrieval.** The atom design describes vector candidate retrieval, generated approach-angle queries, cross-encoder reranking, BM25 rescue, and graph/entity signals. A separate memory-tree path combines FTS5 BM25 and vector cosine with reciprocal-rank fusion, expands one `see_also` hop, and can abstain when similarity or score-gap thresholds are not met. The reusable query wrapper reads node files, returns paths and scores, supports already-shown-result deduplication, and can cap the formatted context length.[[atom retrieval design](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/atom-retrieval-pipeline.md)] [[memory-tree design](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/memory-tree.md)] [[memory-tree code](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_tree.py)] [[query wrapper](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_query.py)]

The query wrapper brackets retrieved text as untrusted reference material with a random per-request sentinel. It also records query/retrieval information in JSONL. These are source-visible prompt framing and diagnostic mechanisms; they do not demonstrate that retrieved claims are correct or that every integration uses the same path.[[query wrapper](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_query.py)]

## Scope isolation

The official architecture and security documentation describe per-conversation-group containers, isolated session files, and mount rules that vary by group type. The indexer resolves an instance vault path separately from its default global configuration, a mechanism documented to avoid multiple instances accidentally sharing the wrong vault. These are host and path boundaries; the inspected material does not establish a tenant-authorization predicate enforced uniformly by every memory database query. Actual group/session propagation and cross-vault isolation remain deployment questions, and no leakage workload was run.[[architecture](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/ARCHITECTURE.md)] [[security model](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/SECURITY.md)] [[indexer](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_indexer.py)]

## Efficiency and observability

The architecture describes local SQLite/FTS and vector-backed retrieval, with local Ollama embeddings for the memory tree and provider alternatives in the memory indexer. The memory-tree decision favors flat vector search at its documented corpus scale and avoids an HNSW index. The atom retrieval design uses a bounded candidate set before a larger cross-encoder reranks; its latency and recall figures are upstream-reported experiments, not this review’s measurements.[[architecture](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/ARCHITECTURE.md)] [[memory-tree decision](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/memory-tree.md)] [[atom retrieval design](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/atom-retrieval-pipeline.md)]

The inspected code/docs expose status, check, graph, calibration and reindex commands plus JSONL retrieval/health logs. Their existence supports local inspection, but does not establish a configured production dashboard, alerting or measured operational reliability.[[memory-tree implementation](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_tree.py)] [[query wrapper](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_query.py)] [[memory indexer](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_indexer.py)]

## Limitations and unknowns

This review is bounded to the files linked above. It did not inspect every memory extractor, mutation path, migration, hook, channel, storage adapter or deployment configuration. Multiple memory paths have distinct indexing and lifecycle behavior, so conclusions about one path should not be generalized to all stored information.[[architecture](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/ARCHITECTURE.md)] [[solution atom schema](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/solution-atom-schema.md)] [[database deletion policy](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/decisions/no-db-deletion.md)]

The deployed vault path, group/session identity propagation, selected embedding/reranker providers, active privacy settings, retention schedules and monitoring configuration are unknown. Source inspection does not establish runtime recall, correctness, complete deletion, actual isolation or performance. The README and design docs contain upstream evaluation reports, which this review did not reproduce.[[README](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/README.md)] [[architecture](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/docs/ARCHITECTURE.md)] [[memory indexer](https://github.com/sliamh11/Deus/blob/2f24c38a2ae42d3161492f0729975b286452f4b4/scripts/memory_indexer.py)] [[metric definitions](../METRICS.md)]
